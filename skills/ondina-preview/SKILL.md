# PR の前の変更を ondina で見せる

ondina は変更を解析し（`ondina analyze`）、ブラウザの画面で見せる（`ondina serve`）。このスキルでは、PR がまだ無い変更（あなたが作った変更）を疑似 PR として見せる。今のブランチに積んだコミットと、コミットしていない変更の両方が入る。

流れ: あなたが解析して画面を開く → レビュアーが画面で変更を理解し、行にメモを書いて締めの画面の「AI に返す」を押す → あなたが `ondina comments wait` で受け取って直す → 解析し直して見せ直す。レビュアーが終わりと言うまで繰り返す。

## やらないこと

- 頼まれていなければ、コミット・push・PR の作成をしない（ondina はコミットしていない変更をそのまま解析する）
- `.ondina/` の下のファイルを直接書き換えない
- `ondina serve` を `--background` 無しで打たない。終わらないうえ、あなたが終わると画面も止まる
- リポジトリを別の場所に複製して解析しない。解析は対象のリポジトリの `.ondina/` に残す（レビュアーの画面がそこを読む）

## 手順

コマンドは対象のリポジトリ（あなたが変更したリポジトリ・worktree）の中で打つ。

### 1. 題と説明を書く

- 題: 1 行。何を変えたか
- 説明: PR 本文と同じ。何を・なぜ変えたか、どう確かめたか（Markdown）。リポジトリの外のファイルに書く（`mktemp` など。リポジトリの中に置くと解析する変更に入る）

### 2. 解析する

```sh
ondina analyze --base <base> --title "<題>" --body <説明のファイル>
```

- `--head` は付けない。`<base>` から分かれた後に今のブランチに積んだコミットと、コミットしていない変更・新しいファイル（git が無視するファイルは入らない）を合わせて解析する。ondina はコミットを作らず、作業ツリー・index・ブランチも変えない
- `<base>` はマージ先のブランチ。言われていなければリポジトリの既定のブランチ（`git symbolic-ref --short refs/remotes/origin/HEAD` の `origin/` を外したもの。取れなければ `main`）。`HEAD` や今のブランチを渡さない（コミット済みの変更が見えなくなる）
- 数分かかる（LLM と言語サーバー）。終わるまで待つ。コマンドの待ち時間に上限を付けられるなら 15 分以上にする（途中で切ると解析が残らない）
- 最後の行が `.ondina/local/<headSha>.json` のパスなら成功
- 失敗したら、出力の最後の数行をそのままレビュアーに伝えて止まる

### 3. 画面を立てて開く（初回だけ）

```sh
ondina serve --background local
open "<URL>"
```

`ondina serve: <URL>` の 1 行が出てすぐ戻る。この worktree の画面が既に動いていれば、新しく立てずにその URL を出す。別の worktree で立てた画面にはこの変更を表示できないので、そのときは空いているポートで新しく立てる（標準エラーにそう出る。失敗ではない）。`open` は開けなくてもよい。

レビュアーに URL を伝え、「画面で変更を見て、行番号の『+』でメモを書き、締めの画面の『AI に返す』を押してください。受け取って直します」と添える。

### 4. 返したコメントを待つ

```sh
ondina comments wait
```

- レビュアーが「AI に返す」を押すまで終わらない。届いているものがあればすぐ終わる
- 終わったら知らせが来る形でバックグラウンドで走らせられるなら、そうする（待つ間もレビュアーと話せる）。できなければ、待ち時間を長く（30 分以上）して待つ
- 途中で切れたら、もう一度打つ。返したコメントは受け取るまで消えない
- 待っている間、画面は「AI に返す」の後に「待っている AI が受け取ります」と出す。待っていなければ「いま待っている AI はいません」と出し、レビュアーは「返したコメントを読んで」と頼む。そう頼まれたらこの手順から始める

出力は JSON:

```json
{
  "comments": [
    { "headSha": "…", "path": "src/main/kotlin/com/example/order/domain/Order.kt", "line": 21, "side": "RIGHT", "startLine": 19, "startSide": "RIGHT", "body": "名前を揃えて", "source": "reviewer" }
  ]
}
```

- `line`（範囲なら最後の行）と `startLine`（範囲の始まり。1 行なら無い）は、その `headSha` の版の行番号。`side` が `RIGHT` なら変更後、`LEFT` なら変更前（base 側）の行
- 今の作業ツリーがその版から変わっていれば、`git show <headSha>:<path>` でその版を読んで場所を合わせる
- `source` が `reviewer` ならレビュアーが書いたメモ、それ以外はレビュアーが採用した AI の下書き

### 5. 直して見せ直す

- 1 件ずつ対応する。直すよう求めるものは直す。質問には答えるだけでよい
- 何をしたかを、1 件ずつ「ファイルと行」「どう直したか（直さなかったなら理由）」でレビュアーに伝える
- 手順 2 の analyze を同じ題で打ち直す（説明を変えたならファイルも書き直す）。画面の上に「新しいバージョン … の解析ができました」と出て、レビュアーが切り替える。画面は立てたままでよい（手順 3 は要らない）
- 手順 4 に戻る。レビュアーが終わり（「OK」「これで PR にして」など）と言ったら待つのをやめる（バックグラウンドの `ondina comments wait` は止める）。その後のコミットや PR の作成は、頼まれたとおりにする

## 権限で失敗したとき

`Operation not permitted` や `EPERM` で失敗したら（サンドボックスで `.git` に書けない・ポートを開けないなど）、権限を上げて同じコマンドを打ち直す（許可を求める）。上げられなければ、打つコマンドをレビュアーに渡して止まる。

## 画面を止めてと言われたら

`ondina serve stop <ポート>`。ポートは手順 3 で出た URL のもの（4177 番が埋まっていたときは別のポートで立っている）。分からなければ `ondina serve list` で動いている画面（ポートとフォルダ）を一覧にし、今いる worktree のフォルダの行のポートを使う。
